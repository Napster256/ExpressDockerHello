# ExpressDockerHello

![ExpressDockerHello Preview](static/DevOps-dockerCover.jpg)

Учебный проект: минимальный Express-сервер «Hello World!», упакованный в Docker-контейнер. Проект создан для ознакомления с Docker и его применением в специализации **AQA (Automation QA)**: контейнеризация приложений, работа с образами и контейнерами через CLI, сборка и отладка.

## Технологии и зависимости

- **node:20-alpine** — базовый образ: Node.js 20 на лёгком Alpine Linux;
- **express** — HTTP-сервер приложения;
- **nodemon** — автоматический перезапуск сервера при локальной разработке;
- **Docker** — контейнеризация и запуск окружения.

### Docker Hub — реестр образов

**[Docker Hub](https://hub.docker.com/)** — официальный публичный реестр Docker-образов, откуда по умолчанию скачиваются базовые образы (как `node:20-alpine` в этом проекте) и готовые приложения. Это аналог npm для контейнеров: тысячи готовых образов для Node.js, Python, MySQL, PostgreSQL и любых других инструментов.

| Команда | Назначение |
|---------|------------|
| `docker pull <образ>` | Скачивание образа из Docker Hub, например `docker pull node:20-alpine`. |
| `docker push <образ>` | Публикация собственного образа в реестр (требует авторизации `docker login`). |


## Dockerfile — что это и зачем нужен

**Dockerfile** — текстовый файл с пошаговыми инструкциями для сборки **Docker-образа**. Он описывает окружение приложения: базовую систему, зависимости, файлы и команду запуска. Образ собирается один раз и затем запускается контейнерами на любой машине с Docker — «работает у меня» превращается в «работает везде».

**Назначение в двух словах:** декларативное и воспроизводимое описание окружения — вместо ручной установки Node.js и зависимостей на каждой машине одна команда `docker build`.

### Ключевые понятия

| Понятие | Описание |
|---------|----------|
| **Image (образ)** | Неизменяемый «слепок»-шаблон, собранный из Dockerfile. |
| **Container (контейнер)** | Запущенный экземпляр образа — живой процесс с файловой системой. |
| **Layer (слой)** | Каждая инструкция Dockerfile создаёт слой; слои кэшируются и ускоряют пересборку. |
| **Build-контекст** | Папка, отправляемая Docker-демону при сборке; `.dockerignore` исключает из неё лишнее. |
| **ENTRYPOINT / CMD** | Команды, которые выполняются при старте контейнера; CMD — команда по умолчанию. |


```dockerfile
FROM node:20-alpine
WORKDIR /app
COPY package*.json ./
RUN npm install
COPY . .
CMD ["node", "index.js"]
```

| Инструкция | Назначение |
|------------|------------|
| `FROM node:20-alpine` | Базовый образ: Node.js 20 на Alpine Linux — лёгкий и быстрый старт. |
| `WORKDIR /app` | Создаёт и устанавливает рабочую директорию внутри контейнера. |
| `COPY package*.json ./` | Копирует манифесты зависимостей для их кэширования слоем сборки. |
| `RUN npm install` | Выполняет установку зависимостей (express, nodemon) на этапе сборки. |
| `COPY . .` | Копирует исходный код проекта в рабочую директорию контейнера. |
| `CMD ["node", "index.js"]` | Команда по умолчанию при запуске контейнера — старт сервера. |

## .dockerignore — что это и зачем нужен

**.dockerignore** — файл-аналог `.gitignore`, но для сборки Docker: перечисляет файлы и папки, которые **не попадают в build-контекст** и, соответственно, не оказываются в образе.

Зачем нужен:

- **ускоряет сборку** — в контекст передаётся меньше данных;
- **уменьшает размер образа** — в него не тащится мусор;
- **защищает от утечек** — секреты (`.env`, ключи) и служебные папки не попадают в образ.

| Запись | Что исключает и почему |
|--------|------------------------|
| `node_modules` | Зависимости ставятся внутри образа командой `RUN npm install` — локальная папка не нужна и раздувает контекст. |
| `.git` | История репозитория не нужна в образе. |
| `.env` | Секреты не должны попадать в образ — переменные передаются при запуске. |
| `*.log` | Логи — временные данные, им в образе не место. |
| `Dockerfile`, `.dockerignore` | Служебные файлы сборки — внутри образа не требуются. |

## Быстрый старт

```bash
# собрать образ
docker build --no-cache . -t test

# запустить контейнер с пробросом порта
docker run -it -p 3000:3000 test node index.js
```

После запуска приложение доступно по адресу `http://localhost:3000`.

## Справочник команд Docker

### Сборка, образы и очистка кэша

| Команда | Описание |
|---------|----------|
| `docker build --no-cache . -t test` | Сборка образа из Dockerfile без использования кэша (чистая сборка), с тегом `test`. |
| `docker images` | Список локальных образов. |
| `docker pull <образ>` | Скачивание образа из реестра (Docker Hub), например `docker pull node:20-alpine`. |
| `docker rmi 9481efe0c1e1` | Удаление образа по ID. |
| `docker builder prune -a` | Полная очистка кэша сборки (build cache). |
| `docker system prune` | Удаление неиспользуемых объектов: остановленных контейнеров, висячих образов, неиспользуемых сетей. |
| `docker system prune -a --volumes` | Глубокая очистка: все неиспользуемые образы, остановленные контейнеры, неиспользуемые сети и тома. |

### Запуск и исследование контейнеров

| Команда | Описание |
|---------|----------|
| `docker ps` | Список запущенных контейнеров. |
| `docker run test bash` | Запуск контейнера из образа `test` с командой `bash`. |
| `docker run test ls` | Запуск контейнера и вывод списка файлов внутри него. |
| `docker run test node -v` | Вывод версии Node.js внутри контейнера. |
| `docker run -it test sh` | Интерактивный запуск контейнера с оболочкой `sh`. |
| `docker run -it --entrypoint sh test` | Интерактивный запуск с переопределением ENTRYPOINT образа на `sh`. |
| `docker run -it -p 3000:3000 test sh` | Интерактивный запуск с пробросом порта: 3000 порт хоста → 3000 порт контейнера. |
| `docker run -it -p 3000:3000 test node index.js` | Интерактивный запуск приложения с пробросом порта. |
| `docker run -it --init -p 3000:3000 test` | Запуск с init-процессом (tini): корректная обработка сигналов и Ctrl+C. |
| `docker run -p 3000:3000 b7df015ff6ae` | Запуск контейнера по ID образа с пробросом порта. |
| `docker --debug <команда>` | Отладочный режим клиента Docker: подробная диагностика вывода. |

### Остановка контейнеров

| Команда | Описание |
|---------|----------|
| `docker stop test` | Плавная остановка контейнера по имени (SIGTERM). |
| `docker stop 7a21f69cea6c` | Плавная остановка контейнера по ID. |
| `docker kill 62ebdbd93d6b` | Принудительная остановка контейнера по ID (SIGKILL). |

### Ключевые флаги

| Флаг | Значение |
|------|----------|
| `-it` | Интерактивный режим с терминалом (stdin + TTY). |
| `-p хост:контейнер` | Проброс портов между хостом и контейнером. |
| `-t` | Присвоить образу тег при сборке. |
| `--no-cache` | Сборка без использования кэша слоёв. |
| `--entrypoint` | Переопределить ENTRYPOINT образа. |
| `--init` | Добавить init-процесс для корректной обработки сигналов. |
| `-a` | Все объекты (для команд очистки). |
| `--volumes` | Дополнительно удалить неиспользуемые тома. |

## docker-compose — назначение и зачем он нужен

**docker-compose** — инструмент для описания и запуска **нескольких контейнеров как одной системы** через файл `docker-compose.yml`. Вместо длинных команд `docker run` с флагами вся конфигурация (образ, порты, тома, переменные окружения, порядок запуска) описывается декларативно в YAML и поднимается одной командой.

**Назначение в двух словах:** оркестрация многоконтейнерных приложений — «приложение + база данных + кэш» поднимаются вместе, с единой сетью и конфигурацией.

В этом проекте необходимость в compose отпала: приложение — один контейнер, и его конфигурация умещается в короткую команду `docker run`. Compose незаменим, когда сервисов становится больше одного.

### Основные директивы docker-compose.yml

| Директива | Назначение |
|-----------|------------|
| `services` | Список сервисов (контейнеров), из которых состоит приложение. |
| `image` | Готовый образ, из которого запускается контейнер сервиса. |
| `build` | Путь сборки образа из Dockerfile (контекст, файл). |
| `ports` | Проброс портов «хост:контейнер», например `"3000:3000"`. |
| `volumes` | Монтирование томов и папок: хранение данных, live-reload кода. |
| `environment` | Переменные окружения контейнера — аналог `.env`. |
| `depends_on` | Порядок запуска сервисов (например, приложение после БД). |
| `command` | Переопределение команды запуска контейнера (CMD). |
| `restart` | Политика перезапуска контейнера (`always`, `unless-stopped`). |
| `networks` | Пользовательские сети для связи сервисов между собой. |

### Основные команды compose

| Команда | Описание |
|---------|----------|
| `docker compose up` | Собрать и запустить все сервисы в фоновом режиме терминала. |
| `docker compose up -d` | То же, в фоновом (detached) режиме. |
| `docker compose down` | Остановить и удалить контейнеры и сети. |
| `docker compose ps` | Список запущенных сервисов. |
| `docker compose logs -f` | Живой просмотр логов сервисов. |
| `docker compose build` | Пересобрать образы, описанные в файле. |

##  Сети и адреса: подключения к базе данных в Docker

В Docker несколько сетевых «слоёв», поэтому адрес подключения всегда зависит от **направления**: кто и к чему подключается. Ниже — все случаи с правильными адресами.

### Сводная таблица направлений

| Кто подключается | К чему | Host | Port |
|------------------|--------|------|------|
| Внешнее приложение на ПК (расширение VS Code, DBeaver) | БД в контейнере | `localhost` или реальный IP машины | проброшенный (левый в `"3307:3306"`) |
| Контейнер (приложение) | БД в соседнем контейнере | имя сервиса в compose (`db`) | внутренний (правый, `3306`) |
| Контейнер | **Внешняя БД на хосте** (мимо Docker) | `host.docker.internal` | порт БД на хосте |

### Случай 1. Внешнее приложение → БД в контейнере

Приложение живёт на вашем компьютере, поэтому идёт через «внешнюю дверь» Docker — проброшенный порт:

```text
Host: localhost          # с того же ПК
Host: 192.168.1.35       # реальный IP машины — с других устройств
Port: 3307               # левый порт из compose ("3307:3306")
```

**Как узнать реальный IP машины:**

| ОС | Команда | Что искать |
|----|---------|------------|
| Windows | `ipconfig` | строку `IPv4-адрес` |
| Linux | `hostname -I` или `ip -brief addr` | адрес физического интерфейса |
| macOS | `ipconfig getifaddr en0` | вывод команды |

**Какой адрес из вывода брать:**

| Интерфейс | Что это | Брать? |
|-----------|---------|--------|
| `lo` | loopback (127.0.0.1) | ❌ |
| `eth0`, `enp*`, `eno*` | проводная сеть | ✅ реальный IP машины |
| `wlan*`, `wlp*` | Wi-Fi | ✅ реальный IP машины |
| `docker0` | внутренний мост Docker (172.17.0.1) | ❌ |
| `br-*` | мосты compose-сетей | ❌ |
| `veth*` | «провода» к контейнерам | ❌ |

**Почему `enp*`, а не `docker0`:** `docker0` — «внутренний коридор» между хостом и контейнерами; его адрес не виден другим устройствам и может меняться или отсутствовать (rootless Docker, кастомные подсети). `enp*`/`wlan*` — «почтовый адрес дома» в локальной сети: по нему машину видят снаружи.

### Случай 2. Контейнер → БД в соседнем контейнере

Внутри Docker-сети контейнеры видят друг друга по **имени сервиса** — встроенный DNS заменяет IP:

```yaml
services:
  app: ...
  db:
    image: mysql:8.0
```

```text
Host: db        # имя сервиса, не localhost и не IP
Port: 3306      # внутренний порт
```

`localhost` внутри контейнера указывает на сам контейнер, а не на соседей и не на хост!

### Случай 3. Контейнер → внешняя база на хосте

Если база данных работает **вне Docker** (MySQL/PostgreSQL установлены прямо на машине), контейнер не достучится до неё через `localhost`. Для выхода «наружу» Docker даёт специальный адрес:

| Платформа | Адрес хоста для контейнера |
|-----------|----------------------------|
| macOS / Windows (Docker Desktop) | `host.docker.internal` |
| Linux | `172.17.0.1` (шлюз docker0) или `extra_hosts: - "host.docker.internal:host-gateway"` в compose |

Пример строки подключения в приложении внутри контейнера:

```js
// Node.js
const dbHost = 'host.docker.internal'; // БД живёт на хосте, не в Docker
```

```php
// wp-config.php
define('DB_HOST', 'host.docker.internal');
```

Порт указывается тот, на котором БД слушает **на хосте** (обычно 3306 / 5432).


### Примечание про Docksal

В окружениях вроде Docksal внешние приложения подключались к отдельному адресу — `192.168.64.100`: это IP **виртуальной машины**, внутри которой Docksal поднимал контейнеры (macOS/Windows). В чистом Docker на Linux виртуалки нет, поэтому отдельного «своего» адреса у окружения не появляется — его роль играет адрес самой машины (`localhost` или IP физического интерфейса).

| Окружение | Адрес для внешних приложений |
|-----------|------------------------------|
| Docksal (macOS/Windows) | `192.168.64.100` (IP виртуалки) |
| Docksal (Linux) | `localhost` |
| Чистый Docker, с того же ПК | `localhost` + проброшенный порт |
| Чистый Docker, с другого устройства | реальный IP машины (`enp*`/`wlan*`) + проброшенный порт |

## Зачем Docker специалисту AQA

- **Воспроизводимость**: одинаковое окружение для тестов локально и в CI — «работает у меня» больше не аргумент;
- **Изоляция**: каждое тестовое окружение живёт в своём контейнере и не конфликтует с другими;
- **Скорость**: развёртывание стенда одной командой `docker run` вместо ручной установки зависимостей;
- **Чистота**: быстрая уборка окружения через `docker stop` и `docker system prune`.
